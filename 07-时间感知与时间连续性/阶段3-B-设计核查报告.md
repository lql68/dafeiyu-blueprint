## 一、时间范围过滤是否覆盖所有检索来源

### 1.1 实际调用链（源码证据）

**主链路入口**：`memory_engine_crud.py:422`
```python

    self,

    session_id: str | None = None,
```

**它调用两条路**（`memory_engine_crud.py:473-505`）：

```python

    results = await self.dual_route_retriever.search(
```

| 检索器 | 文件:行 | 签名 | 时间参数 |
|---|---|---|---|
| `HybridRetriever.search` | `core/retrieval/hybrid_retriever.py:125` | `(query, k=10, session_id=None, persona_id=None, diagnostics=None, *, relevance_only=False)` | ❌ 无 |

**结论：主链路四个检索器全部不支持时间过滤。**

### 1.3 过滤发生在哪一层

`filter_source_time()` 只被**两条**路调用：

```
core/managers/memory_engine_agentic.py:153
    results, unknown = filter_source_time(results, start_ts, end_ts)

core/managers/memory_engine_participant.py:138
    batch, unknown = filter_source_time(batch, start_ts, end_ts)
```

**这两处都在 `search_memories_agentic()` 内部，即融合之后、返回之前。**

**而 `search_memories_agentic()` 不是主链路** —— 它只被 `memory_agentic_search_tool.py`（LLM 工具调用）使用。

主链路 `search_memories()` **从不经过它**。

### 1.4 会不会混入超范围记忆

**会。百分之百会。**

主链路没有任何时间过滤，`search_memories(query, k, session_id, persona_id)` 返回的是**纯语义相关 + 时间衰减排序**的结果。用户问「上个月我们讨论过什么」，返回的可能是上周或去年的记忆。

### 1.5 时间未知的记忆会不会被错误丢弃

**当前不会** —— 因为不过滤。

**但如果把 `filter_source_time` 直接套到主链路，会**。它的实现（`agentic_recall_types.py:77-95`）：

```python
def filter_source_time(results, start_ts, end_ts):
    if start_ts is None and end_ts is None:
        return results, []
    kept, unknown = [], []
    for r in results:
        metadata = r.metadata or {}
        start = parse_source_timestamp(metadata.get("source_time_start"))
        end = parse_source_timestamp(metadata.get("source_time_end")) or start
        if start <= 0:                          # ← 没有 source_time 的进 unknown
            unknown.append(r)
            continue
        if start_ts is not None and end < start_ts:
            continue
        if end_ts is not None and start > end_ts:
            continue
        kept.append(r)
    return kept, unknown
```

**它把 `unknown` 单独返回，不丢弃** —— 设计是对的。**调用方决定怎么用**。

### 1.6 能否复用到主链路

**能，且不需要改它本身。**

理由：
- 它的输入是 `list[HybridResult]` + 两个 `float | None` —— 主链路返回的正是 `list[HybridResult]`
- 它只读 `r.metadata["source_time_start/end"]` —— 主链路的 `HybridResult.metadata` 里**有**这两个键（由 `_apply_source_time_tags` 写入）
- 它不依赖任何 agentic 上下文

**唯一需要补的**：主链路函数签名加 `start_ts/end_ts`，融合后调一次。

### 1.7 风险等级

| 项 | 风险 |
|---|---|
| 主链路无时间过滤 | **高**（用户问「上个月」会拿到任意时间的记忆） |
| `filter_source_time` 可复用但未接 | 低（接口是干净的） |
| `unknown` 语义 | 低（设计已对） |

## 二、`documents.metadata.source_time_*` 的实际生成规则

### 2.1 生成模块

### 2.2 完整实现（逐行）

```python
def _apply_source_time_tags(
    self,
    content: str,
    metadata: dict[str, Any],
    messages: list[Message],
) -> str:
    """Attach source dates without asking the LLM to infer them."""
    if not self.config.get("include_source_time_tags", True) or not messages:
        return content

    timestamps = sorted(float(message.timestamp) for message in messages)
    start = datetime.fromtimestamp(timestamps[0]).astimezone()
    end = datetime.fromtimestamp(timestamps[-1]).astimezone()
    dates = sorted({
        datetime.fromtimestamp(value).strftime("%Y-%m-%d")
        for value in timestamps
    })
    label = dates[0] if len(dates) == 1 else f"{dates[0]} - {dates[-1]}"

    metadata["time_tags"] = dates
    metadata["source_time_start"] = start.isoformat()
    metadata["source_time_end"] = end.isoformat()
    metadata["source_time_label"] = label
    return content          # ← content 原样返回，没打标签
```

### 2.3 七个问题的逐一回答

| # | 问题 | 实际答案 | 证据 |
|---|---|---|---|
| 1 | 哪个模块生成 | `MemoryProcessor._apply_source_time_tags` | `memory_processor.py:575` |
| 2 | LLM 抽取 / 规则 / 其他 | **纯规则**。docstring 明确写 `without asking the LLM to infer them` | `:581` |
| 3 | 时间表达如何转时间戳 | **不解析任何时间表达**。直接取这批消息 `message.timestamp` 的 min/max | `:585-587` |
| 4 | 是否用 `temporal.tz()` | **否**。用 `datetime.fromtimestamp(ts).astimezone()` = **系统本地时区** | `:586-587` |
| 5 | 精度是否保留 | **否**。`isoformat()` 输出微秒级字符串，看起来精确到微秒，但实际只是「消息发送时刻」 | `:597-598` |
| 6 | 是否把记录时间当事件时间 | **是**。`message.timestamp` 是**消息发送时间**。用户说「昨天我去钓鱼」，`source_time_start` = **今天他发这条消息的时刻** | `:585` |
| 7 | 模糊/缺失/失败时如何处理 | `not messages` → 提前 return（**不写任何字段**）；`float(message.timestamp)` 若非法 → `ValueError` 未捕获；`timestamps` 非空由 `not messages` 保证 | `:582-585` |

### 2.4 一个额外的发现

方法名叫 `_apply_source_time_tags`，**但它只写 `metadata`，`return content` 是原样返回**。所以：
- `metadata["time_tags"]` = `["2026-11-14"]` 这类日期列表
- `metadata["source_time_label"]` = `"2026-11-14"` 或 `"2026-11-13 - 2026-11-14"`
- **`content` 里没有任何时间标记**

如果下游指望 `content` 里有日期，是拿不到的 —— 只能读 `metadata`。

### 2.5 配置开关

`include_source_time_tags`（默认 `True`），在 `core/plugin_initializer_finalize.py:298-299` 读取：
```python
"include_source_time_tags": self.config_manager.get(
    "reflection_engine.include_source_time_tags", True
)
```
**注意路径不一致**：写入时读 `self.config.get("include_source_time_tags")`（顶层），初始化时读 `reflection_engine.include_source_time_tags`（嵌套）。**这两个可能不是同一个值。**

### 2.6 已实现 vs 推测

**已实现（源码直证）**：
- ✅ 字段生成、三个键的内容、调用点
- ✅ 纯规则不调 LLM
- ✅ 用系统本地时区
- ✅ `content` 不被修改

**推测（未跑实机验证）**：
- ⚠️ `message.timestamp` 在 QQ 适配器下的实际值 —— 应为消息发送时间，但没抓一条真实记录比对
- ⚠️ `include_source_time_tags` 两个配置路径是否联动 —— 没读到实际配置值

### 2.7 风险等级

| 项 | 风险 |
|---|---|
| 消息时间当事件时间 | **高**（这是「把记录时间当事件时间」的直接来源） |
| 用本地时区不用 `temporal.tz()` | **中**（值一致但换机器会漂） |
| 精度丢失 | **中**（`isoformat` 误导性） |
| 两个配置路径不一致 | **低**（开关默认都是 true） |

## 四、对阶段 3-B 设计的影响

### 4.1 影响一：不能只改 atom 层

审计报告原本假设「补 atom 层 + 接线」。**核查发现主链路是两条路并行**：
- `documents` 层（hybrid / dual_route）
- `atoms` 层（atom_retriever，**只补充 parent 不在已有结果里的**）

**时间过滤必须在「两路合并之后」做一次**，否则：
- 只过滤 atom → documents 结果漏网
- 只过滤 documents → atom 补进来的漏网

**改法**：`search_memories()` 末尾（`results` 拼装完、return 前）调一次 `filter_source_time`。

### 4.2 影响二：`source_time_*` 已经是「消息时间」

`_apply_source_time_tags` 写的是 `message.timestamp`，**主链路的时间过滤会按「消息发送时间」筛**，不是「事件发生时间」。

**但这恰恰是 3-B 要修的核心** —— 不能改 `_apply_source_time_tags`（它会破坏 agentic 已用的 `source_time_*` 语义），**而是在 `memory_atoms` 层新建 `event_time` + `time_precision`，让两个时间并存**：
- `documents.metadata.source_time_*` = **消息时间**（保留不动）
- `memory_atoms.event_time` + `time_precision` = **事件时间**（3-B 新建）

**过滤时用哪个？** 建议：
- 有 `event_time` 且 `precision != unknown` → 用它
- 否则退回 `source_time_start`（消息时间），但**在上下文里标注「这是记录时间，不是发生时间」**

### 4.3 影响三：`filter_source_time` 需要「两字段兼容」

现有实现只读 `metadata["source_time_start"]`。如果 atom 层要按 `event_time` 过滤，**要不要改 `filter_source_time`？**

**建议：不改它**。新建一个 `filter_by_event_time()` 平行函数，主链路用新的，`agentic` 保持旧的。理由：
- 改它会动 agentic 的已验证行为
- 两个函数各管一层，语义清晰

### 4.4 影响四：`_parse_event_time` 的 `now` 来源

现在 `now = time.time()`（本地无 tz）。3-B 换成 `temporal.now()` 时：
- 时区从「系统本地」变成「`DFY_TZ` 或 Asia/Shanghai」
- **如果两者不一致，边界会漂**

**需要确认**：机器系统时区是什么？如果就是 Asia/Shanghai，那没差别。

## 六、尚无法确认的内容

1. **`message.timestamp` 在 QQ 适配器下的实际值** —— 应为消息发送时间，但没抓真实记录比对（可以查 `data_v4.db` 的 `platform_message_history` 确认）。
2. **`include_source_time_tags` 两个配置路径的实际值** —— 没读 `cmd_config.json` 对应节。
3. **`documents.metadata.source_time_*` 的实际填充率** —— 审计只见 3 条样本，没统计 475 条里有多少有这三个键。
4. **`filter_source_time` 的时间比较是否处理「区间重叠」** —— 代码是 `end < start_ts → 丢` / `start > end_ts → 丢`，即**部分重叠就算命中**。这个语义对不对要用户确认。
5. **主链路加 `start_ts/end_ts` 会不会影响缓存** —— `_search_cache_key(query, k, session_id, persona_id)` 不含时间参数，加了要同步改 key，否则会命中过期缓存。

## 七、结论

**核查回答了三个问题**：

1. **主链路四个检索器全部无时间过滤**；`filter_source_time` 只存在于 agentic 那条路，在融合后调用；**可以复用到主链路，但必须在两路合并之后调一次**，不能只改 atom 层。

2. **`source_time_*` 是「消息发送时间」**，纯规则生成、不用 LLM、用系统本地时区、精度不保留、**确实是「把记录时间当事件时间」的直接来源**。3-B 不改它，另建 `event_time` 并存。

3. **`event_time` 只有 5 个测试**；缺失 8 项（昨天/前天/后天/上周/跨年/纯时段词/模糊时间/`event_time≠created_at`）；**有一个真实失败** `test_classify_unknown_type`（代码改了测试没跟）；**23 个 async 失败是环境问题不是代码问题**。

**风险最高的两条**：主链路无过滤 / `source_time_*` 用消息时间。

**对 3-B 的最大影响**：原计划改 7 个文件，**要加到 9 个**（多 `memory_engine_crud.py` 和 `agentic_recall_types.py`），因为过滤必须落在两路合并之后。
