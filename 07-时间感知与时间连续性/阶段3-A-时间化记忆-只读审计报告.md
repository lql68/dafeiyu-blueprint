## 四、`event_time` 的真实填充情况（审计重点）

```
总数 1431
created_at           非空 1431 (100.0%)
event_time           非空   24 ( 1.7%)   ← 关键
last_accessed_at     非空 1431 (100.0%)
last_reinforced_at   非空  518 (36.2%)
expires_at           非空 1431 (100.0%)
```

按类型：
```
episodic    899 条 → 5 条有 event_time (0.6%)
factual     287 条 → 0
planned     196 条 → 19 (9.7%)
preference   38 条 → 0
relational   11 条 → 0
```

**24 条里 13 条的 `|created_at - event_time| < 2 秒`** —— 一半以上等于把记录时间当成了事件时间。

**根因（读 `atom_classifier.py` 得到）**：
```python
_TIME_INDICATORS = re.compile(
    r"明天|后天|大后天|昨天|前天|今天|"
    r"(?:上周|本周|下下周|下周)?周[一二三四五六日天]|"
    r"上周|本周|下下周|下周|"
    r"下个?月|上个?月|明年|后年|去年|前年|"
    r"\d{1,2}月\d{1,2}[日号]|\d{4}年\d{1,2}月|"
    r"上午|下午|晚上|凌晨|早上|中午|傍晚|"      # ← 这些命中 has_time
    r"\d{1,2}[点时：:]\d{1,2}"
)

def _parse_event_time(text):
    # 只处理：前天/昨天/今天/明天/后天/大后天（±N×86400）
    #       周X（_parse_weekday_time）
    #       上周/本周/下周/下下周（±N×86400）
    #       \d{1,2}月\d{1,2}日
    return None    # ← 其余全部 None
```

**问题链**：
1. `"下午在看书"` → `has_time=True`（命中「下午」）
2. `_parse_event_time` **解析不出**（它不处理纯粹时段词）→ `event_time=None`
3. 走 `if has_action: return EPISODIC, 0.75, None`
4. **`event_time` 丢掉，只留下 `created_at`**

**另一个问题**：`"昨天"` 返回 `now - 86400` —— 是「现在这一刻减 24 小时」，不是「昨天零点」。精度是 ±1 天，但存成秒级 float，**看起来像精确时间**。

## 六、写入 → 存储 → 读取的完整调用链

### 写入
```
AstrBot 消息
  └ conversation_manager._resolve_event_timestamp(event)   → event.message_obj.timestamp
       （非法/超前 >300s 返回 None，回退接收时间）
  └ memory_processor（LLM 抽取 key_facts + topics + participants）
       └ atom_classifier.classify_atoms(key_facts)
            └ _classify_single(fact)
                 ├ has_time = _TIME_INDICATORS.search(text)
                 ├ event_time = _parse_event_time(text) if has_time
                 └ 分支：
                     has_time + has_action + 过去 → EPISODIC 0.80, event_time
                     has_time + has_action + 未来 → PLANNED  0.85, event_time
                     has_preference → PREFERENCE 0.82, None
                     has_relation   → RELATIONAL 0.80, None
                     has_stative    → FACTUAL   0.78, None
                     has_action     → EPISODIC  0.75, None
                     兜底           → EPISODIC  0.55, None
            └ compute_ttl(atom_type, importance, 0, event_time)
       └ atom_store.INSERT（19 列，含 event_time）
```

### 读取
```
search_memories(query, k, session_id, persona_id)            ← 主链路
  └ hybrid_retriever
      ├ vector_retriever
      ├ bm25_retriever
      ├ graph_retriever / graph_keyword_retriever
      └ atom_retriever.search()      ← 无时间参数
  └ RRF 融合 → list[HybridResult]

search_memories_agentic(..., start_ts, end_ts)               ← 另一条
  └ _agentic_search_conversation / _by_participant
      └ filter_source_time(results, start_ts, end_ts) → (kept, unknown)
```

### 注入
```
voice_server.think()
  └ POST AstrBot /turn → main.py:_turn
      └ lm.initializer.memory_engine.search_memories(query, k=5, session_id=umo)
      └ mem_block 拼进 system
```

## 八、迁移与回滚

- **迁移方式**：`PRAGMA table_info(memory_atoms)` 查列 → 缺哪列 `ALTER TABLE memory_atoms ADD COLUMN time_precision TEXT DEFAULT 'unknown'` / `temporal_status TEXT DEFAULT 'unknown'`
- **旧数据兼容**：两列默认值 `'unknown'`，**不动任何历史行**
- **备份**：迁移前 `shutil.copy2` 到 `livingmemory.db.bak-t3-<ts>`
- **回滚**：SQLite 不支持 `DROP COLUMN`（3.35 才支持）→ 备份文件还原即可；或加 `_deprecated` 后缀标记
- **可重复执行**：迁移函数先查列存在性，重复跑无副作用

## 九、尚未解决的问题

1. **`_parse_event_time` 的粗粒度**：「昨天」= `now-86400`（不是昨天零点）。要改成按 `temporal.tz()` 算日历边界。
2. **`documents` 与 `memory_atoms` 的时间不联动**：`documents.metadata.source_time_*` 已经是对的，`memory_atoms.event_time` 是另算的。
3. **`autobiography` 零值章节**（#26）：写章节时 `from_ts/to_ts` 传了 0。
4. **`graph_nodes.created_at` 是 TEXT**：三格式之一，本阶段不动。
5. **`parse_time_bound` 只吃 ISO**：「上个月」要靠模型自己换算（当前 schema 描述已明确要 ISO）。

## 十、审计结论

**一句话**：时间化的**骨架已经有一半**（`source_time_*` 元数据 + `filter_source_time` + `search_memories_agentic(start_ts, end_ts)`），**缺的是** ①`time_precision` 字段 ②atom 层的时间过滤 ③主链路接线 ④中文时间词到区间的解析。

**最小可行改动 = 2 个新列 + 1 个解析函数 + 3 处接线**，不需要重写、不需要新表。
