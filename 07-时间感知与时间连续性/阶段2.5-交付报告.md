
**为什么选 `req.system_prompt` 而不是 `extra_user_content_parts`**：

- `extra_user_content_parts` 在 AstrBot 里已经是「系统提醒」的位置，再塞一条会变成两个 `<system_reminder>` 块，语义重复
- `system_prompt` 是模型看到的最底层指令，加在末尾最稳
- **但查重时要两边都看** —— 万一以后有人往 parts 里塞了时标

`ProviderRequest`（`core/provider/entities.py:95`）的字段：`prompt` / `session_id` / `image_urls` / `audio_urls` / `extra_user_content_parts` / `func_tool` / `contexts` / **`system_prompt`** / `conversation` / `tool_calls_result` / `model`。

## 三、时间上下文示例

### 场景 A：AstrBot 已注入日期（**当前配置就是这种**）

AstrBot 给：`Current datetime: 2026-11-12 23:29 (CST), Weekday: 周四`

插件补：`【现在的时间】深夜 23:29。`

→ **模型看到的完整时间**：日期 ✅ 星期 ✅ 时分 ✅ 昼夜 ✅

### 场景 B：AstrBot 的 `datetime_system_prompt` 被关掉

插件补：`【现在的时间】现在是2026年11月12日 周四 深夜 23:29。`

→ 和语音通道**完全一致**的格式（都走 `temporal.context()`）

### 为什么分两种

`req.system_prompt` 和 `extra_user_content_parts` 都会被拼进模型输入。如果不管三七二十一全塞：

```
Current datetime: 2026-11-12 23:29 (CST), Weekday: 周四   ← AstrBot
【现在的时间】现在是2026年11月12日 周四 深夜 23:29。      ← 我
```

**同一天出现两种写法**，模型会当成两个不同信息源。所以先查 `"Current datetime:" in seen`，有就只补时间缺的那两样。

## 四、时区统一情况

### 唯一入口：`temporal.tz_name()`

`dafeiyu-core/src/dafeiyu/kernel/temporal.py:56-57`

```python
DEFAULT_TZ = "Asia/Shanghai"
TZ_ENV = "DFY_TZ"
```

**读 `DFY_TZ` 环境变量，缺省 `Asia/Shanghai`。** 解析顺序：`zoneinfo` → `_FALLBACK_OFFSETS`（仅全年无夏令时的时区）→ `TzError`。

### 已统一的模块

| 模块 | 怎么读 |
|---|---|
| `voice_server.py` 的 `/temporal` | `TEMPORAL.tz_name()` |
| **插件 `_qq_time_bit()`**（本次） | 同一个 `temporal` 模块 |
| `dafeiyu.kernel.rhythm` | 通过 `temporal.band()` 间接 |

### **没有**统一的模块（明确记录）

| 位置 | 现在怎么读 | 为什么不改 |
|---|---|---|
| `astrbot/core/astr_main_agent.py:1015` | `zoneinfo.ZoneInfo(cfg["timezone"])`，值来自 `cmd_config.json` | **AstrBot 内核代码**，改了会被上游覆盖；且它只管自己那段 `<system_reminder>` |
| `astrbot/core/config/default.py:157` | `"datetime_system_prompt": True` | 配置默认值，不是时区 |

**当前两处值一致**（都是 `Asia/Shanghai`）。**风险**：哪天有人只改一边，网页说东八区、QQ 说别的。

**统一方案（留待后续）**：把 `cmd_config.json:timezone` 设成空，让 AstrBot 回退到 `now.astimezone()`（系统时区）；或写个启动脚本把 `DFY_TZ` 和 `cmd_config.json:timezone` 一起设。

### naive / aware 混用检查

- `temporal.now()` **一律带 tz**（`datetime.now(tz())`）
- `temporal.now_utc()` **返回 float**（epoch 秒），从源头避免 datetime 比较
- `elapsed(ts, now_ts)` 两个参数**都是 float**
- 本次新增的 `_qq_time_bit()` **只调 `t.now()` 拿字段**（`.hour` / `.minute`），不做任何跨时区比较

**测试里也有一条守着**：`test_改环境变量后内容跟着变` 用 `t.tz().utcoffset(t.now())`，不是 `utcoffset(None)`（后者对 aware datetime 返回 `None`，第一版就踩了这个）。

## 五、上次交流时间：**QQ 通道无法可靠提供**

### 检查结果

| 可能来源 | 有没有 | 能不能用 |
|---|---|---|
| 插件自己的 `_sent_day` / `_sent_n` | 有 | ❌ 那是「主动发消息计数」，不是「他最后说话时间」 |
| `warmth_state.json.at` | 有 | ❌ 每次 `/turn` 写，含网页通话，不代表 QQ |
| `world_state.json.last_at` | 有 | ❌ 那是「她走到哪儿的时刻」 |
| `emotion_state.json.updated_at` | 有 | ❌ 每次情绪更新，可能是她自己的想法 |
| `req.contexts` 里的历史消息 | 有 | ❌ **OpenAI 格式没有时间戳**，只有 role/content |
| AstrBot 的会话记录 | 有 | ❌ 要另起查询，且不区分「他说的」和「她说的」 |

**结论：没有一个「他上次在 QQ 上说话的时刻」。**

### 所以本阶段怎么处理

`_qq_time_bit()` 调 `temporal.context(0)` —— **传 0，明确表示「不知道间隔」**。

`temporal.context(0)` 的实现（`temporal.py`）：

```python
if last_active_ts and last_active_ts > 0:
    gap = ...
    parts.append("你上次和他说话，是" + fmt_gap(gap))
```

`0` 走假值分支，整句不出现。**不是伪造一个「刚刚」，是压根不提。**

### 留到阶段 5

要可靠提供，得有个「他最后说话时刻」的持久化。选项：

1. 插件内存字典 `{session_id: ts}` —— **重启即失忆**，但比现在强
2. 写进现有 JSON（`warmth_state.json` 加一个 `last_heard_at`）—— 不动数据库，但语义混进「温度」
3. 新建一张表 —— **用户明确禁止**

**留给阶段 5 决定。**
