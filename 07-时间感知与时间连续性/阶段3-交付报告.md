## C. 时间解析能力

### 已支持（13 类，实测全对）

| 表达 | 精度 | 状态 | 说明 |
|---|---|---|---|
| `2026年11月10日` | exact | past | 绝对日期 |
| `5月30日` | approximate | future | 无年份，取最近一次，label 带「（年份未说明）」 |
| `今天下午在看书` | exact | past | 相对日 + 时段词 → 取时段区间 |
| `昨天我去钓鱼` | exact | past | |
| `明天见` | exact | future | |
| `大前天` / `后天` / `大后天` | exact | past/future | **按词长降序匹配**（否则「大后天」被「后天」抢先） |
| `上周` / `本周` / `下周` | exact | past/future | 整周，周一起算 |
| `下周二` / `上周三` | exact | future/past | 带前缀 |
| `周二` | approximate | — | 光星期不带前缀 |
| `去年夏天` | approximate | past | 季节，冬天跨年 |
| `去年` / `今年` | exact | past | 整年 |
| `前段时间` / `最近` / `前几天` | relative | past | 30 / 14 / 7 天窗口 |
| `小时候` / `以前` / `有一天` | unknown | unknown | 不猜 |

### 暂不支持

| 表达 | 当前行为 | 原因 |
|---|---|---|
| `下午看书` | **unknown**，label「下午（具体哪天没说）」 | 按设计不默认成今天 |
| `三点半` | unknown | 纯时刻无日期 |
| `前天上午十点左右` | exact（整天） | 「左右」的模糊度没建模 |
| `下个月 15 号` | unknown | 「下个月」+ 日期的组合没解析 |
| 英文日期 | unknown | 只做中文 |
| 跨时区事件 | 按 `temporal.tz()` 统一解释 | 没有「事件发生时区」概念 |

### 时间语义

- `time_precision`：exact / approximate / relative / unknown（**四档，无第五种**）
- `temporal_status`：past / future / unknown（**不做 ongoing**）
- 左闭右开 `[start, end)`
- 部分重叠即命中（mode = any）

### 关键设计：为什么不拿 `source_time_*` 当事件时间

`source_time_start/end` 是 `MemoryProcessor._apply_source_time_tags()` 用 `message.timestamp` 的 min/max 写的 —— **那是「他什么时候说的」，不是「事情什么时候发生的」**。

所以 `filter_by_event_time()` **只认 `metadata["atom_event_time"]`**。document 层没有这个字段 → 进 `unknown` 不丢弃。

### unknown 的处理

```python
results = _m + _u     # matched 在前，unknown 在后
# excluded 直接丢掉（事件时间明确且不在区间内）
```

unknown 排在 matched 后面而不是删掉 —— 用户问「上个月我们在聊什么」时，那些没解析出时间的记忆仍在候选里，只是不排前面。

### 修测试时改的 3 处（都跟随已确认的语义变更，不是降标准）

1. **`test_atom_store_lifecycle`** —— P0 引入 `effective_age`（时间压缩）后，「1000 秒前创建」压缩成 0.0000001 天，永远不过期。改成 **700 天前 + 显式 `ttl_days=30`**（700 天压缩封顶 90 天，90 > 30 才该过期）；并且 `created_at` 要跟 `expires_at` 一起 override —— **`insert()` 会用 `time.time()` 重算 `created_at`**，只 override `expires_at` 是不够的。
2. **`test_lifecycle_manager_logs_and_backs_off_on_error`** —— P0 加退避后，重试走 `logger.warning("[AtomLifecycle] 第 %d/%d 次维护失败…")`，不是旧的 `logger.error("维护任务异常")`；退避首值是 **2.0s** 不是 60s。
3. **`test_classify_unknown_type`** —— 2026-11-01 的 unknown 迁移把兜底从 `UNKNOWN 0.60` 改成 `EPISODIC 0.55`（已批准的变更），测试跟随。

## G. 遗留问题

### 真实存在的（都有具体现象）

1. **`livingmemory/tests/` 全量跑超时**
   单独跑 `test_memory_atom.py + test_p3_event_time.py` 是 87 passed / 2.05 秒；但 `pytest tests/` 跑到 10 分钟仍不结束（已手动终止）。
   怀疑是 `tests/integration/test_real_db_end_to_end.py` 连真库 + 真 embedding 在等网络。**没有定位到具体哪个用例**，因为加 `--durations` 那次也超时了。

2. **5 项从审计阶段就无法确认**
   - QQ 适配器下 `message.timestamp` 的实际值（没抓真实消息比对）
   - `include_source_time_tags` 两个配置路径（顶层 vs `reflection_engine.` 嵌套）的实际值
   - 475 条 documents 里有多少有 `source_time_*`（只见过 3 条样本）
   - `filter_source_time` 的「部分重叠」语义在 agentic 链路上是否真的符合预期
   - 缓存 key 的 `round(..., 3)` 够不够（毫秒级，理论上够）

3. **没有端到端跑过真实检索**
   「问『上个月我们讨论过什么』能按事件时间筛」这条**没有在活着的服务上验证**。原因：`voice_server` 的 `think()` 目前**还没有把用户的时间词转成 `start_ts/end_ts` 传给 `search_memories`** —— 这一层接线属于阶段 4（记忆检索增强），不在阶段 3 范围。
   阶段 3 交付的是**能力**（`search_memories` 支持时间参数 + 过滤函数可用 + 测试覆盖），不是**自动接线**。

4. **`parse_cn_time` 的「下个月 15 号」「三点半」不解析**
   见 C 节的「暂不支持」表。这两个在实际对话里会出现，属于可扩展项。

### 不是问题的

- 13 条「假事件时间」：历史遗留，已用 `unknown` 精度隔离，不回填
- `filter_source_time` 丢弃 unknown 只计数：那是 agentic 链路的既有行为，本次不动
