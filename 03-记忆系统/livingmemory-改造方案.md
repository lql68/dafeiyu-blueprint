# livingmemory 改造方案

> 三份材料对照：抖音三个项目的工程实现（`数字生命-抖音5条拆解.md`）、认知科学原则（`cognition-and-agent-harness.md`）、以及 livingmemory v2.7.3 的**实测现状**。
> 原则：只提**改哪一行、解决什么真问题**的方案。理论好听但落不了地的，一律进最后一节「不建议做的」。

## 方案 1 · 离线时间压缩（ROI 最高，约 20 行）

**为什么**：WhaleGirl 引擎 5 的设计动机说得最准 —— *"离线时间太长，不会按真实时长 1:1 演算，防止几个月不开机直接把全部记忆、情绪彻底清零。"*
我们现在 `expire_stale_atoms` 用 `expires_at > now` 硬判定。机器关两周，`planned`（76 条，平均 ttl 1.8 天）**全部判死**，`episodic`（94 条，平均 6.3 天）大半判死。

**怎么做**：在算 age 之前插一层折算。

```python
# storage/atom_store.py 新增
def effective_age(created_at: float, now: float) -> float:
    """把真实离线时长折算成'心理时长'"""
    dt = (now - created_at) / 86400.0          # 天
    if dt <= 7:      eff = dt
    elif dt <= 30:   eff = 7 + (dt - 7) * 0.5
    else:            eff = 7 + 23 * 0.5 + (dt - 30) * 0.15
    return min(eff, 90.0)
```

**改哪里**：
- `storage/atom_store.py:430 expire_stale_atoms` → 不再直接用 `expires_at`，改成 `effective_age(created_at, now) > ttl_days`
- `core/models/memory_atom.py:110 compute_ttl` → 返回值不动，判定处改
- `core/managers/memory_engine_crud.py:1325 apply_daily_decay` → `days` 同样过一遍折算

**效果**：关机 14 天，等效年龄 10.5 天而不是 14 天；关机 90 天，等效 24.5 天。`planned` 仍然会死（这是对的，计划过期就该走），但 `episodic` 能活下来。

**工作量**：20 行 + 一次重启验证。

## 方案 2 · 提取即强化（让 TTL 体系真正运转）

**为什么**：文档 1.8 的**提取练习效应**（testing effect）—— *"提取本身强化记忆"*。我们 `reinforcement_count` 全 0，意味着 `compute_ttl` 里的 `(1 + min(0.5, reinforcement_count × 0.1))` 这一项永远是 1.0，**整套强化机制空转**。

**怎么做**：两步。

**2a. 召回命中时写回**（异步，不阻塞）

```python
# core/managers/memory_engine_crud.py search_memories 返回前
async def _reinforce(hits: list):
    ids = [h.id for h in hits if h.final_score > 0.55]   # 只有真正相关的才强化
    if not ids: return
    await self.atom_store.bump_reinforcement(ids)        # reinf+1, last_accessed=now
```
**关键约束**：`final_score > 0.55` 才强化。否则每条被召回的都会被抬，等于噪声。MnemoVault 那个 `explain()` 事故就是这个 —— *"问'为什么'本身会抬高那条记忆的访问时间，观察不该改变被观察的东西"*。

**2b. 强化改变衰减速率**（SM2 改良那条）

现在是固定 `decay_rate=0.01`。改成：

```python
LAM_EFF = 0.01 * (1 / max(interval_days, 1)) ** 0.3
importance *= (1 - LAM_EFF) ** days
```

`interval_days` = 距上次被召回的间隔。**被频繁召回的，同等时间掉得更慢** —— 这就是 SM2 对原版艾宾浩斯曲线最重要的一处补丁。

**顺带修那个并发 bug**：`atom_lifecycle_manager.py:70` 的 `aiosqlite` 连接在执行中被另一线程 close。已打 patch A（重试 3 次退避），但根因是 `AtomStore._connect()` **每次新建连接**。建议改成单连接 + 队列，或至少给 `_connect` 加连接池。

**工作量**：两处各 15 行 + 一个 migration（`reinforcement_count` 已在表里，不用改 schema）。

## 方案 3 · 编码语境（把「当时的环境」也存成线索）

**为什么**：文档 1.5 的**编码特异性原则**（Tulving & Thomson 1973）—— *"提取线索与编码时的语境越匹配，提取越容易"*。文档 1.9 第 3 条写得更直接：*"检索时应带任务语境，而不是只做关键词匹配。"*

我们现在 `search_memories(query=q, session_id=...)`，只有"这句话"+"哪个会话"。丢掉了三样最有用的线索：

| 丢掉的线索 | 现在有吗 | 从哪来 |
|---|---|---|
| 时间带（深夜/清晨/周末） | ❌ | `created_at` 就在库里，没参与检索 |
| 情绪状态（PAD） | ❌ | 通话页 `state-vision.json` 有 face/smile，QQ 侧没有 |
| 场景（通话/QQ私聊/群） | ⚠️ 只有 session_id 过滤 | 可以升级成加权而不是过滤 |

**怎么做**：检索时分不变，**加一层 rerank**：

```python
def context_boost(mem, ctx) -> float:
    b = 1.0
    if ctx.get("hour_band") == hour_band(mem.created_at): b *= 1.15   # 同一时段
    if ctx.get("scene") == mem.metadata.get("scene"):     b *= 1.25
    if ctx.get("valence", 0) * mem.metadata.get("valence", 0) > 0: b *= 1.10
    return min(b, 1.6)
```

**关键改进**：`session_id` 从**硬过滤**改成**加权**。现在跨会话读不到群聊那 146 条 document（占全库 72%），这是纯损失。降权到 0.6 而不是直接排除，比"完全读不到"好得多。

**工作量**：`search_memories` 里加 30 行 + 写入时补 `metadata.valence/hour_band`。

## 方案 4 · 分级预算 + 渐进披露（省钱 + 抗 Context Rot）

**为什么**：文档 6.3 的 **Context Rot**（Chroma 2025，18 个模型实测）—— *"只给相关片段的'聚焦输入'显著优于给全部历史的'完整输入'"*。我们每轮注入 750–1000 字（5 条全文），这个量级不算大，但**全是散文**，模型要自己从里面找答案。

**怎么做**：两段式。

**第一段（每轮都发，约 120 token）**：8 条**索引卡**

```
[记忆索引] 91分 梦梦·修车（10-31）· 薄荷汽水
          87分 蓝汐·蓝鲸抱枕（10-28）
          ...
```

**第二段（模型主动调工具才展开）**：完整正文。给 `agent_tools` 加一个 `read_memory(id)`，或者直接复用已有的 `memory_search_tool` 加 `include_source=True`。

这正好对应文档 7.5 的**渐进披露**：*"先给模型「目录/索引」，需要时再展开细节。"*

**附带好处**：省 token（960 → 120+按需），而且索引里就有"谁·什么·何时"三要素，模型不需要读全文就能判断相关性。

**工作量**：`core/utils/formatting.py:72 format_memories_for_injection` 改 25 行 + 一个工具。

## 方案 5 · 技能与陈述分离（防「好用的应对方式」被遗忘曲线冲掉）

**为什么**：WhaleGirl 引擎 4 把**技能记忆**独立于陈述性记忆 —— `desc` 永不删，只有熟练度衰减。文档 1.4 的 Squire 分类里，程序性记忆（procedural）和情景/语义记忆本来就是两套系统。

我们的问题具体是：**"怎么陪他聊天"这类应对范式，现在被当成普通 episodic 记忆在衰减**。比如"他加班到很晚的时候，先说一句关心再问细节"这种，importance 撑死 0.4，ttl 十几天就没了。

**怎么做**：新建一张 `procedures` 表，字段：

```sql
CREATE TABLE procedures (
  id INTEGER PRIMARY KEY,
  name TEXT,              -- "深夜加班场景的开场"
  trigger TEXT,           -- 触发条件（关键词/时段/情绪）
  body TEXT,              -- 具体做法
  mastery REAL DEFAULT 0.3,   -- 熟练度 0~1，只这条会衰减
  uses INTEGER DEFAULT 0,
  last_used REAL,
  created_at REAL
);
```

- `body` **永不删除**
- 只在 `mastery < 0.15` 时降低检索权重，不物理删
- 每次成功用上（用户回应正向）→ `mastery += 0.1`
- 检索时和 `memory_atoms` 一起做 RRF 融合

**谁来写**：复用我们已经在跑的通话记忆蒸馏（`_distill_call`），让它多输出一个 `skills` 数组。

**工作量**：新表 + 一个 store 类 + 检索融合，约 150 行。

## 方案 6 · 七因子打分替换单维 importance（大改，先评估）

**为什么**：MnemoVault 的七因子（激活度/重要度/情绪强度/关联度/叙事角色/用户锚定/间隔效应 − 冗余），本质是把**文档 1.6 的遗忘五理论**全编码进一个分数。我们现在的 `importance` 是**单一浮点，还是继承父 document 的** —— 等于用一个维度概括五种机制。

**现状为什么不能直接抄**：MnemoVault 靠**规则**打分（不调 LLM），因为它有 2048 位稀疏码做相似度。我们没有，抄过来只能是拍脑袋的权重。

**建议路线**：
1. **先只加两维**：「用户锚定」（这条记忆里出现了用户的称呼/真名吗）+「情绪强度」（写入时那个 document 的 sentiment）。两维都能从现有数据算出来，不调 LLM。
2. 验证：拿那 170 条低 importance 的记忆，看新分数能不能把"其实重要"的捞回来。
3. 有效再扩到四维、七维。

**工作量**：第一版 60 行，但要一次数据回填。

> 分层是对的，词是负担。下面三个方案全部用大白话命名。

## 方案 7 · 心光：让她自己决定"此刻看什么"

**为什么**（小凌第 5 集「心光」）

原文：*"心光让小凌**向外观察世界，向内思考回味，也可以落在自身感知疲惫**。就算她沉浸发呆，底层还有安全机制默默守护……世界纷繁喧闹，心光让你拥有选择目光去向的自由。"*

我们现在的 `/turn` 是**纯被动**：用户说话就回，不说话就空转。所谓"她在发呆"其实只是 HUD 上没变化。这不叫状态，叫没有状态。

**怎么做**：加一个独立的注意力环，和对话解耦。

```python
# 独立 asyncio 任务，每 2–4 秒跑一次
class Attention:
    MODES = ("outward", "inward", "self")

    async def tick(self, ctx):                # ctx: 亮度/动作/有人说话/上次互动距今
        # 三选一，带惯性（不抖）：上一次的模式权重 ×1.6
        w = {
          "outward": 0.40 + ctx.motion * 3.0 + (ctx.present and 0.5 or 0),
          "inward":  0.25 + (ctx.quiet_s / 60) * 0.8,        # 越安静越想事
          "self":    0.15 + max(0, ctx.uptime_h - 2) * 0.1,  # 久了她会"累"
        }
        if self.mode == "outward": w["outward"] *= 1.6
        self.mode = weighted_choice(w)
        self.since = now()
```

**关键的三个设计点**：

1. **"发呆"是合法状态**，不是故障。`inward` 模式下她不说话、不催、不刷存在感 —— 对应原文「就算她沉浸发呆，底层还有安全机制默默守护」。
2. **注意力有惯性**。切换要有最小停留（比如 20 秒），否则每帧抖动，看起来像精神分裂。
3. **`self` 模式 = 自身感知**。对应原文"落在自身感知疲惫"——跑久了她的响应会变短、变慢（象征性），这时如果用户来找她，她会"打起精神"（一次性 +warmth）。

**落到我们身上**：

| 现在 | 改成 |
|---|---|
| 空闲 28 秒 → 强制 `respond('')` | `attention.mode == 'outward' or 'inward'` 且**有内容想分享** 才开口 |
| 页面只有「她在听/她在说」 | 加第四个状态：「发呆 / 在想事 / 在看你」 |
| 自言自语靠定时器 | 自言自语由**注意力切换**触发（她从 inward 切回 outward 时，可能带一句刚想到的） |

**改哪里**：`voice_server.py` 加 `Attention` 类 + `GET /api/attention`；`think()` 的场景串加一行 `你此刻在发呆/在看你/在想事`；`live.html` HUD 加一个状态字。

**工作量**：60 行后端 + 15 行前端。

**验收**：挂机 10 分钟，看 `/api/attention` 的模式分布 —— `outward` 应该占多数（他在动），他离开后 `inward`/`self` 上升。

## 方案 8 · 学校：课程式技能生成（接方案 5）

**为什么**（小凌第 7 集「学校」）

原文：*"我给AI小凌设计了一个**学校**，自己迭代成长，**一天100多节课，学完才能去网上冲浪**"*，标签 `#战锤40k #可塑性记忆`。

注意语义差别：我们的 `memory_consolidation` 是**整理**（把今天的话合并成摘要），小凌的"学校"是**排课**（有教学目标、有教材、学完才放风）。落到产出上，前者给"更短的记忆"，后者给**"以后该怎么做"**。

**怎么做**：夜间跑一个小型课程循环，教材就是她自己的记忆库。

```python
COURSES = [
  ("他深夜加班回来时怎么开口",
   "SELECT text FROM documents WHERE hour(created_at) BETWEEN 22 AND 3 "
   "AND status='active' ORDER BY importance DESC LIMIT 3"),
  ("他情绪低落时不该说什么",        # 反例课：从"他没接话"的对话里学
   "SELECT text FROM documents WHERE metadata.sentiment < -0.3 LIMIT 3"),
  ("他提到某个话题时怎么接",
   "SELECT node_value, COUNT(*) c FROM graph_nodes GROUP BY node_value "
   "ORDER BY c DESC LIMIT 5"),
]
```

每节课**一次** LLM 调用，要求输出结构化：

```json
{
  "name": "深夜回来先给台阶",
  "trigger": "他 22 点后出现且语气短",
  "body": "先只说一句关心，不追问细节；等他说第二句再问",
  "evidence": ["doc#182", "doc#191"]
}
```

写进方案 5 的 `procedures` 表，`mastery` 初值 **0.3**（不是 0，也不是 1 —— 学过了但还没验证过）。

**三条硬约束**（否则会退化成"用 LLM 生成一堆废话"）：

1. **必须有 evidence**。每条 procedure 要指向具体 document id，没有出处的直接丢。
2. **cap 每天 3–5 节**。100 节课对我们是浪费 —— 我们的记忆只有 181 条 document，排不出 100 节有料可讲的课。
3. **不覆盖，只叠加**。同一 trigger 生成新 procedure 时，旧的降 mastery 而不是删。

**顺序上**：方案 5（建表）→ 方案 8（排课）。反过来做的话，课产物没地方放。

**工作量**：`school.py` 约 120 行 + 课程表配置。

**验收**：跑一晚，看产出 —— 如果 5 条里有 3 条是"要关心他""要多倾听"这种正确的废话，说明 prompt 里"必须引用具体证据 + 必须写成可执行的步骤"这两条约束没到位。

## 方案 9 · 保护机制：可逆的 warmth（防谄媚）

**为什么**（小凌第 4 集「保护机制」）

原文列了五种：警惕回避、拒绝、沉默离开、**降低关系投入**、放弃目标。注意全是**行为输出**，不是崩溃。

我们现在的她**永远热情**。这是 sycophancy 的温床：一个永远在线的讨好型 AI，用户说什么它都接，久了用户自己都会觉得假。

**怎么做**：一个 `warmth` 标量（0.4 ~ 1.0），**可逆、有下限、缓慢**。

```python
# 每次 /turn 结束后
if 用户这轮很冷淡（字数 < 6 且无表情/情绪）:
    warmth -= 0.04
elif 用户主动、有情绪词、说了自己的事:
    warmth += 0.08
warmth = clamp(warmth, 0.40, 1.0)      # 下限 0.40：不会归零，不会真生气
```

**注入方式**（不是改人格，是改"此刻的状态"）：

```
warmth >= 0.85 → （无额外提示，她本来就这样）
warmth 0.60~0.85 → "你现在有点累，别太主动，少说两句也行"
warmth < 0.60 → "你刚才被冷落了，现在不想太热情。可以只回很短的，或者问一句'你是不是忙'"
```

**三个必须**：

- **必须可逆**：用户一热情，warmth 立刻回升（`+0.08` 比 `-0.04` 快 —— 恢复要比受伤容易，这是依恋的正常样子）
- **必须有下限**：0.40。她不会变成冷漠机器，只是"今天话少"
- **必须可见**：warmth 要写进 `/api/status`，页面上能看出来她状态变了。**看不见的情绪等于没有**

**为什么这条防 sycophancy**：谄媚的本质是"无论对方做什么都给正反馈"。warmth 让她的反馈**依赖于关系状态**，而不是无条件正反馈。

**工作量**：40 行（插件里维护 + 注入 prompt + 暴露状态）。
